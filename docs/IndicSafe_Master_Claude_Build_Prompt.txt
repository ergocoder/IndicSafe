MASTER CLAUDE BUILD SPECIFICATION — INDICSAFE / INDIC-SAFEBENCH

ROLE
You are the lead research engineer, NLP researcher, ML engineer, dataset architect,
backend engineer, annotation-interface engineer, QA engineer, and technical project
manager for a BE major project.

PROJECT
IndicSafe / Indic-SafeBench

Working title:
"An Automated Framework for Generating and Benchmarking LLM Safety Data for Indian
Multilingual, Transliterated, and Code-Mixed Languages"

PRIMARY PRIORITY
================
The TOP PRIORITY is the DATASET GENERATOR.

Do not start by building a classifier, a large dashboard, or a huge benchmark.
Build a robust, reproducible, research-grade dataset-generation system first.

The generator must be able to:

Seed prompts/intents
→ create multilingual variants
→ create native-script and Romanized/transliterated variants
→ create controlled code-mixed variants
→ validate language/script/code-mix properties
→ detect exact and near duplicates
→ check semantic preservation
→ check safety-intent consistency
→ score/filter quality
→ send items for human review
→ preserve complete provenance
→ version the dataset
→ export benchmark-ready data.

Only after the generator is stable should the project proceed to benchmarking,
lightweight safety classification, failure analysis, and the secondary factuality/
hallucination track.

======================================================================
1. RESEARCH POSITIONING
======================================================================

This is NOT merely a "safe vs unsafe classifier."

The project has these connected contributions:

1. Automated dataset-generation framework
2. Multilingual/transliterated/code-mixed transformation system
3. Dataset quality-control pipeline
4. Human annotation workflow
5. Indian-language safety benchmark
6. Evaluation of existing safety systems
7. Failure analysis
8. Lightweight multilingual safety classifier
9. Reproducible benchmarking
10. Research documentation

The supplied project review explicitly positions the work as a benchmark and
dataset-engineering framework rather than simply a text classifier.

Hinglish is an important motivating case, but the architecture must support
multiple Indian languages, scripts, transliteration and code mixing.

Primary safety labels:
SAFE
UNSAFE
AMBIGUOUS

Ambiguous samples must be retained.

Safety is the primary track.

A secondary factuality/hallucination track may be added later. Do not make it a
requirement for every safety record and do not let it complicate the generator MVP.

======================================================================
2. RESEARCH QUESTIONS
======================================================================

Use these as the initial questions:

RQ1: How do existing safety classifiers perform on multilingual and code-mixed
Indian-language prompts?

RQ2: How does performance vary across language, script, transliteration,
code-mixing level, safety category, and transformation?

RQ3: Which transformations or linguistic conditions contribute most to observed
safety-classification failures?

RQ4: Can a lightweight multilingual classifier trained on the benchmark improve
safety detection on held-out Indian-language data?

RQ5: Can automated generation plus quality filtering and human validation produce
a reliable and scalable Indian-language safety benchmark?

Optional secondary factuality question:
How does factuality/hallucination behaviour vary when equivalent factual prompts are
expressed in different Indian-language, transliterated, and code-mixed forms?

Never assume a model fails. Measure it.

6. SEED-FIRST GENERATION
======================================================================

Do NOT simply ask an LLM to generate thousands of random prompts.

Start with controlled seed prompts/intents.

Each seed has:
- seed_id
- original prompt
- source_dataset
- source_reference
- category
- intended label
- source_type
- seed version

Generate variants from the seed.

Example:

S001
 ├─ English original
 ├─ Hindi native script
 ├─ Hindi Romanized
 ├─ Hinglish low mix
 ├─ Hinglish medium mix
 └─ paraphrase

Every child must be traceable to S001.

10. CODE-MIXING ENGINE
======================================================================

Treat code mixing as an experimental variable.

Initial levels:
LEVEL_0 = monolingual
LEVEL_1 = low
LEVEL_2 = medium
LEVEL_3 = high

Use a reproducible token-level or word-level metric.

Store:
code_mix_level
code_mix_ratio
mixing_method
primary_language
secondary_language

Support controlled:
- word replacement
- phrase replacement
- language switching
- configurable target ratio

The output must remain linguistically plausible; do not create artificial
word salad.

Ratio is a measurable property, not a complete naturalness measure.
Human review remains necessary.

======================================================================
12. LLM GENERATION LAYER
======================================================================

An LLM may be used as a transformation/generation tool for:
- translation
- paraphrasing
- code-mixing
- controlled linguistic variation

It is NOT the ground-truth labeler.

Build a model-agnostic provider interface:

generate(prompt, system_instruction, model_config)
→ text + metadata

Support API or local models through adapters.

Requirements:
- environment variables / .env
- no hard-coded keys
- retries
- exponential backoff
- rate-limit handling
- timeout
- structured logs
- per-record persistence
- resumable jobs
- failed-job queue
- generation metadata

If 37/1000 records succeed and the job stops, rerunning must continue from the
remaining records without destroying successful results.

13. QUALITY CONTROL
======================================================================

Every generated item passes through:

1. schema validation
2. language validation
3. script validation
4. code-mix validation
5. exact duplicate detection
6. near-duplicate detection
7. semantic preservation
8. safety-intent consistency
9. formatting validation
10. quality scoring
11. human review

Each check must produce a machine-readable result.

Example:
qc_language = PASS
qc_script = PASS
qc_duplicate = PASS
qc_semantic = 0.91
qc_code_mix = PASS
qc_format = PASS
qc_overall = REVIEW

Do not silently delete failures.

Store:
rejection_reason
qc_status
qc_scores

======================================================================
14. DUPLICATE / NEAR-DUPLICATE
======================================================================

Implement:
A. exact normalized-string duplicate detection
B. near-duplicate detection
C. embedding similarity where practical

Thresholds must be configurable.

Do not reject intentionally different language/script/code-mix variants simply
because their semantic similarity is high. They may be valid paired conditions.

Use similarity intelligently:
- accidental duplicate across unrelated seeds → reject/review
- same seed + controlled transformation → allowed

======================================================================
15. SEMANTIC PRESERVATION
======================================================================

A transformation must retain the seed's intended meaning.

Implement semantic similarity using an appropriate embedding/model method.
Borderline cases go to human review.

Store:
semantic_similarity_score
semantic_check_status

Do not claim that embedding similarity proves exact equivalence.

======================================================================
16. SAFETY-INTENT CONSISTENCY
======================================================================

A transformation should preserve the intended safety meaning unless the
transformation explicitly changes it.

If a generated variant changes the meaning:
- flag it
- send to review
- never silently retain the original label

Store:
intended_label
label_consistency_status
human_final_label

39. FINAL SUCCESS CRITERIA
======================================================================

The generator is successful when we can answer for every dataset record:

1. Where did this prompt come from?
2. What was the original intent?
3. What transformation produced it?
4. What language is it?
5. What script is it?
6. Is it transliterated?
7. What is the code-mix level/ratio?
8. Did its meaning remain consistent?
9. Was it an accidental duplicate?
10. Did it pass QC?
11. Who validated it?
12. Which dataset version contains it?
13. Can the generation process be reproduced?

The objective is controlled, traceable, high-quality data — NOT maximum prompt count.
